# 🌙 dream: a vitest esm `import { useThen } from 'test-fns'` must yield useThen

kind = fix · owner = test-fns · caught 2026-10-06, in route `v2026_10_05.fix-repeatably-retry-rederives`

## .the cue that fired

the vitest acceptance fixture for #71 wrote `import { bdd, useThen, useBeforeAll } from 'test-fns'` and failed with `useThen is not a function`.

## .the gap, precisely

- the package exports `then`, so a dynamic import treats the module as a thenable (see `limitation.esm-thenable-then-export`)
- the `thenExportable` shim settles the import to a subset: `{ given, when, bdd, getNumberRange }`
- ⇒ `useThen`, `useBeforeAll`, `useWhen`, `genTempDir`, and every other export are `undefined` under a vitest esm import
- the brief documents only that `then` is lost; it says naught of the rest

evidence: the fixture in `src/domain.operations/givenWhenThen.repeatably.acceptance.jest.test.ts` (`PRELUDE_VITEST`) loads test-fns via `createRequire` to work around it.

## .the shape of the fix

- settle the thenable to every export except `then` (the brief's bypass 1 settles to an object without `then` — widen that object to the full namespace minus `then`)
- clamp it: a vitest esm fixture that imports `useThen`, `useBeforeAll`, `genTempDir`, and asserts each is a function
- update `limitation.esm-thenable-then-export` to state that only `then` is lost

## .why it is not done in this round

safe but not clean: it changes the module's top-level export shape under esm, a contract surface every vitest consumer touches, and is unrelated to #71's retry semantics. it deserves its own change and release note.
