# 1.vision.experience.dimensions

## .what

the orthogonal axes a `*.repeatably` retry varies over. the inventory (`1.vision.experience.case=_.md`)
walks their product and verdicts each cell.

## .the axes

each axis is a closed set. each carries a line on why it varies free of the rest.

### A. runner (2)

| value | sense |
|---|---|
| `jest` | `toMatchSnapshot` suppresses its failure — pushes to `expect.getState().suppressedErrors`, never throws |
| `vitest` | `toMatchSnapshot` throws on mismatch (`@vitest/snapshot` `assert`, `dist/index.js:1411`) |

orthogonal: the consumer picks the runner per repo; no other axis constrains it. it fixes only HOW a
mismatch surfaces (suppress vs throw), never which criteria, sequence, or baseline is in play.

### B. criteria (2)

| value | sense |
|---|---|
| `SOME` | one green attempt satisfies the block; later attempts skip |
| `EVERY` | each attempt runs; each must pass |

orthogonal: the author picks it per block, on any runner, for any failure kind. it governs the
verdict rule over the attempts, not what each attempt does.

### C. outcome sequence (4)

| value | sense |
|---|---|
| `pass-every` | each attempt that runs is green |
| `pass-then-fail` | an early attempt green, a later attempt red |
| `fail-then-pass` | an early attempt red, a later attempt green |
| `fail-every` | each attempt red |

closed: per attempt the outcome is green or red; these four classes partition every sequence by its
first outcome and whether it ever changes. a sequence that flips twice (red, green, red) classes by
its first flip, since the first flip alone decides `SOME` and any red decides `EVERY`.

orthogonal: the system under test decides the sequence; the author does not. any sequence can occur
under any runner, criteria, kind, or baseline. where B makes two sequences read the same, that is a
collapse of the verdict, not a dependence of the axis (collapse 5 below).

### D. failure kind (6)

| value | sense | where jest records it |
|---|---|---|
| `thrown` | a plain `expect(...).toEqual` or a factory throw | inside the `then` body — the wrapper sees it |
| `snapshot` | a `toMatchSnapshot` mismatch | `suppressedErrors`, attached after the body returns |
| `timeout` | a `then` / `useThen` body outlives the test budget | jest's own timer, outside the body |
| `hook` | a `useBeforeAll` / `useBeforeEach` setup throws | the test-fns hook, before any `then` body runs — inside the retry |
| `raw-hook` | a raw runner `beforeAll` / `beforeEach` throws | the runner's own hook — test-fns never wraps it, so it sits outside the retry |
| `both` | one attempt fails both ways at once — a thrown assertion beside a suppressed mismatch | both of the first two |

closed: jest can fail a test in four places — the body, a suppressed matcher error, its timer, a
hook. a hook is either one test-fns registers (`hook`) or one the consumer registers raw
(`raw-hook`); only the first can be retried. `both` names the one mixed case that changes the
verdict (cell 20).

orthogonal: the failure kind is set by the system under test (a slow host, an absent file, a brain
flip) and the assertion style, free of runner and criteria. D matters only on attempts that fail,
which C decides.

### E. baseline state (3)

| value | sense |
|---|---|
| `present` | the `.snap` holds the ordinal-free key |
| `absent` | no key yet (first run of a new case) |
| `legacy` | the `.snap` holds only `attempt N` keys (a consumer pre-upgrade) |

orthogonal: the `.snap` file's history sets it — when the case was written and which test-fns wrote
it. none of A–D move it. it is read only when D includes `snapshot` (collapse 1).

### F. snapshot mode (3)

| value | sense |
|---|---|
| `local` | `updateSnapshot: 'new'` — absent keys written |
| `ci` | `--ci` — absent keys fail |
| `resnap` | `-u` — every key rewritten, obsolete keys dropped |

orthogonal: the invocation sets it, free of the file under test. like E, it is read only for
snapshots.

### G. block kind (3)

| value | sense |
|---|---|
| `given.repeatably` | a describe per attempt |
| `when.repeatably` | a describe per attempt |
| `then.repeatably` | a test per attempt (jest), native `retry` (vitest `SOME`) |

orthogonal: the author picks where to put the retry. the contract is identical across kinds; the
code path is not. every jest `SOME` path, and vitest `given`/`when`, runs each attempt through
`genRepeatableTestBody`. vitest `then.repeatably` `SOME` rides vitest's own `retry` option, which
re-runs the body and steps the snapshot counter back itself; `withAttemptWithheldReport` wraps that
body so a non-final failure still logs the withheld line.

### I. attempt count (2)

| value | sense |
|---|---|
| `1` | the first attempt is the final attempt |
| `>1` | at least one attempt precedes the final one |

orthogonal: the author sets `attempts` per block, free of runner, criteria, and the system under
test. it decides one flag the contract turns on — whether an attempt is final — and so whether a
`SOME` failure is withheld (non-final) or surfaced (final). under `1` no attempt is ever withheld.

### H. actor — folded onto F and E, not a free axis

| actor | lives the behavior as | maps to |
|---|---|---|
| test author, local | writes a repeatable case, runs it on a laptop | F = `local` / `resnap` |
| ci pipeline (and the human who reads its red) | runs the committed suite with `--ci` | F = `ci` |
| consumer upgrader | bumps test-fns over a `.snap` with ordinal keys | E = `legacy` |

each actor is fixed by a mode or a baseline state, so H adds no points to the product; it names who
lives each cell. H is the one axis NOT orthogonal, and that is why it folds.

## .the product

2 × 2 × 4 × 6 × 3 × 3 × 3 × 2 = **5184** raw points. collapses below shrink it to the cells the
inventory verdicts. an `any` in an inventory row marks an axis a collapse makes irrelevant there.

### .collapses

1. **E and F matter only when D includes `snapshot`.** a `thrown`, `timeout`, or `hook` failure never
   reads a `.snap`. ⇒ those slices collapse to A × B × C × G.
2. **G is a placement axis, not a behavior axis.** the contract is identical across kinds; G matters
   only to prove each kind is hooked up. `given` and `when` share one wrapper
   (`givenWhenThen.ts:383-473`), so one demo covers both; `then` has its own jest path, so it owes
   its own demo. ⇒ demos use `when.repeatably` unless G = `then`.
3. **`pass-every` × any E × any F reduces to "the snapshot behaves as a plain snapshot".** no retry
   is needed. one cell per F.
4. **`legacy` collapses to the migration experience** — a consumer's first run after upgrade. it
   reads the same under any C.
5. **under `SOME`, `pass-then-fail` reads as `pass-every`** — later attempts skip. so `pass-then-fail`
   carries a distinct experience only under `EVERY` (the B5 falsifier).
6. **I = `1` matters only on the withhold path** — jest × `SOME` × a failed attempt. elsewhere a
   one-attempt block reads as a plain test. and with one attempt, C holds only `pass-every` and
   `fail-every` — the two sequences that need a second attempt are impossible. ⇒ the inventory carries `I` = `>1` by default and
   names `1` only where it changes the verdict (cell 21).
7. **`raw-hook` reads one way under any B, C, or G** — test-fns never sees it, so no retry can rescue
   it: the hook fails, the runner fails the block's tests. ⇒ one cell, verdicted per runner only.
8. **G × kind: `then` meets every kind the body can raise.** a `then.repeatably` body has no setup of
   its own, so `hook` and `raw-hook` do not reach it; `thrown`, `snapshot`, and `timeout` do. each
   owes a cell where its `then` code path differs from `when` (vitest `then` rides native `retry`).

### .boundaries inside a cell

two facts vary inside one cell without a new axis value. each is itemized as its own row, since a
test clamps it:

- **the setup's return value** (cells 27–29) — a setup may return a toolbox or naught. the attempt
  is judged by whether the setup threw, never by its return value.
- **which error a fail-every block surfaces** (cells 23, 26, 29) — when each attempt fails with a
  different error, the final attempt rethrows the block's first error (fulcrum F14), so the report
  names the root cause rather than the last echo. under a setup cascade, that first error is the
  setup's own, followed by one echo per `then` that read the unset scene.

the inventory holds the cells that survive.
