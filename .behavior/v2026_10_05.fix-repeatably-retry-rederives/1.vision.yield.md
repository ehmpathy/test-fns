# 1.vision — a repeatable retry that actually retries

## 🔴 .the headline — one failed attempt fails the whole block

**when any attempt of a `when.repeatably({ criteria: 'SOME' })` block times out, the file fails —
even after a later attempt passes.** the same holds for a setup that throws and for a snapshot that
mismatches. the retry exists to absorb exactly these failures, and absorbs none of them.

**the cause:** the `SOME` wrapper absorbs only an error thrown **inside a `then` body**
(`try/catch`, `givenWhenThen.ts:445-461`). jest records three failures **outside** that body, where
the wrapper cannot see them, and each one reds the file. measured in this repo (jest 30.2.0, scratch
probe, 2026-10-05, `attempts: 3`, `criteria: 'SOME'`, removed after the measure):

| failure on attempt 1 only | where jest records it | drives | today |
|---|---|---|---|
| a `useThen` factory exceeds the jest timeout | jest's own timer | 2 | 🔴 attempt 2 re-drives and passes, yet the file is **red** — jest marked attempt 1's `useThen` test `✕ Exceeded timeout`, and no later pass erases that |
| a `useBeforeAll` setup throws (`ENOENT`) | the hook, before any `then` body | **1** | 🔴 jest fails the `then` with no call into its body; the wrapper sees no error, `afterAll` marks the attempt **passed**, attempts 2–3 skip. the file is **red** and the retry never ran |
| a `toMatchSnapshot` mismatches | `expect.getState().suppressedErrors` — jest's matcher never throws (`jest-snapshot/build/index.js:1535-1537`); jest-circus attaches it after the body returns (`jest-circus/build/jestAdapterInit.js:2036-2042`) | **1** | 🔴 as the hook row: attempt 1 marked passed, attempts 2–3 skip, the file is **red** |

the same shapes reddened `ehmpathy/rhachet-roles-bhrain` on 2026-10-05
(`.agent/repo=.this/role=any/briefs/howto.deflake-live-brain-tests.md`, bhrain pr #567): *"attempt
1 and 2 timed out at 180s, attempt 3 passed → file red: 2 failed"* and *"attempt 1 threw `ENOENT`,
attempts 2 and 3 passed → file red: 2 failed"*. that consumer gave up on `when.repeatably(SOME)` for
`jest.retryTimes(2)`, with the note *"a jest timeout also fires outside any in-test wrapper, so no
attempt can catch it"*.

⇒ **the fix: a non-final `SOME` attempt absorbs every failure jest would record against it — a throw,
a timeout, a setup failure, a suppressed snapshot mismatch — and only the final attempt may report
one.** fulcrum `F6`, ruled by the wisher: all in one change.

### .what #71 got right, and what it got wrong

#71 named the symptom (one drive, then no-ops) and blamed `useThen` for a cache across attempts. the
probe shows `useThen` re-drives per attempt; its "128 ms / 13 ms drives" are skip markers after a
snapshot mismatch the wrapper never saw. fulcrum `F1`.

| bar | #71 says today | measured today |
|---|---|---|
| B1 factory runs N× | counter reads 1 | ✅ **3 of 3** — `useThen` re-drives per attempt |
| B4 fail-then-pass under SOME | red | ✅ **green** for a thrown failure; 🔴 red for a snapshot, timeout, or setup failure |
| B5 pass-then-fail under EVERY | open | ✅ **red** — D3 is not a defect |
| B2 key carries ordinal | yes | 🔴 **yes** — `... when: snap, attempt 1 then: stable 1` |

so the fix also strips the attempt ordinal from the snapshot key (B2), so every attempt checks one
baseline and `--ci` does not hard-fail attempts 2+ on an absent key. `useThen` stays as is.

## .the outcome world

### before

a consumer wraps a real-brain suite in `when.repeatably({ attempts: 3, criteria: 'SOME' })`. in ci
the host is slow: attempt 1's ask runs past 180s. jest marks attempt 1 `✕ Exceeded timeout`. attempt
2 asks again and passes — and the file is red anyway. on another file a setup throws `ENOENT` on
attempt 1: attempts 2 and 3 skip, never run, and the file is red. on a third, a brain flip
mismatches a snapshot: the same skip, the same red; and had attempt 2 run under `--ci`, it would
hard-fail on the absent `attempt 2` key. the retry is a label. the consumer turns to
`jest.retryTimes`.

### after

each failure of attempt 1 — the overrun, the setup error, the mismatch — is withheld, logged, and
the attempt marked failed. attempt 2 re-drives — a fresh ask, a fresh setup, a fresh verdict — and
any snapshot compares against the **one** ordinal-free key. green; under `--ci`, exit 0. on a real
regression every attempt drives, and only the final attempt's failure surfaces, with jest's normal
output.

### the aha

the log changes from a red `✕` followed by `🫧 [skipped] prior repeatably attempt passed`, to:

```
🫧 [withheld] attempt 1 failed, a retry follows: exceeded the 180000ms budget
```

and a green attempt 2. the run holds no `✕` from a rescued attempt. a consumer can drop
`jest.retryTimes` and trust `when.repeatably` again; the `.snap` file loses `, attempt 1` from each
key and gains no copies.

## .the contract

| behavior | jest | vitest |
|---|---|---|
| a timeout in a non-final `SOME` attempt (a `then` or `useThen` body that outlives its budget) | the wrapper owns the deadline: it races the body against the test's own budget (the per-test timeout, else the configured one) and turns an overrun into a caught failure, withheld like a throw. it registers the jest test with a slightly larger timeout, so jest's own timer never fires first. the overrun drive is not cancelled (js cannot); its late result is discarded | the same deadline race inside the wrapper; vitest's own timer likewise sits past it |
| a `useBeforeAll` / `useBeforeEach` setup failure in a non-final `SOME` attempt | `usePrep` catches it, marks the attempt failed, logs `🫧 [withheld]`, and does not rethrow — the attempt's `then` blocks read the unset proxy, throw, and are withheld in turn. on the final attempt it rethrows, so jest reports the hook failure as today | same |
| a raw jest `beforeAll` / `beforeEach` that throws inside a repeatable block | not absorbed — test-fns does not own it. the readme says so and points to `useBeforeAll` | same |
| a snapshot mismatch in a non-final `SOME` attempt | read from `suppressedErrors`, withheld, attempt marked failed, `snapshotState.unmatched` restored — required: an `unmatched` count fails the whole run even when every test is green (`@jest/core/build/index.js:1091,1162`) | already throws → already caught; no change |
| any withheld failure (thrown, timeout, setup, or snapshot) of a non-final `SOME` attempt | the test still reports ✓ (jest has no "retried" status), so the wrapper logs `🫧 [withheld] attempt N failed, a retry follows: <first line of the error>` — today a swallowed failure leaves no trace | same |
| any failure in the final attempt (incl. `attempts: 1`, where attempt 1 is final) | surfaces as today — the throw, the timeout, the hook error, or jest's snapshot diff; never withheld | surfaces as today |
| `then.repeatably` jest `SOME` (its own `try/catch`, `givenWhenThen.ts:539-545`) | the same absorb as the given/when wrapper: suppressed-error read and deadline race | n/a — vitest uses native `retry`; that it re-runs a timed-out try is assumed, and the probe for open question 8 confirms it |
| the snapshot key in any `given` / `when` / `then` `.repeatably` block | carries no `attempt N`; one key per assertion, shared by all attempts. built from the recorded ordinal-free name of the block (the wrapper knows the `desc` it suffixed) — never a regex over the full name, which would mangle a user title like `'gives up, attempt 3 is the cap'` | same |
| the per-name snapshot counter | reset at each attempt start, so attempt 2's first snapshot is `... 1` again | same, via vitest's own state |
| the reported test name | keeps `, attempt N` — a human still sees which attempt ran | same |
| an absent ordinal-free key whose `, attempt N` twin sits in the `.snap` | the failure carries a test-fns hint: the key was renamed; run once with `-u` and commit | same |
| a jest without the expected snapshot-state shape | `MalfunctionError` that names the jest version and the absent field | n/a |
| `EVERY` | no skip-on-success (unchanged — verified) | unchanged |
| `useThen` | unchanged — already re-drives per attempt | unchanged |

## .mental model

- **to a friend:** "a retry now really retries. if attempt 1 times out, blows up in setup, or flips
  a snapshot, attempt 2 gets a clean shot — and only the last attempt can fail the file."
- **analogy:** a race with false starts allowed — a false start sends the runners back to the
  blocks; only a fault in the final start disqualifies. today a single false start ends the race.
- **their words vs ours:** they say "retry", "flaky", "timed out", "resnap"; we say "attempt",
  "withheld failure", "budget", "ordinal-free key". the docs speak theirs.

## .evaluation

**pros**
- the retry rescues what it promises to — a slow host, a flaky setup, a flipped snapshot alike
- consumers can drop `jest.retryTimes`, which retries every test in a file, for a retry scoped to
  the blocks that declare it
- one baseline per assertion — the `.snap` shrinks and no longer claims coverage it lacks
- no `useThen` contract change; the fix sits in the `SOME` wrappers, `usePrep`, and one key rule

**cons**
- reads jest internals (`suppressedErrors` public; `_counters`, `unmatched` underscore/semi-private;
  the test budget, per open question 8) — fail-fast if absent (`F2`)
- every consumer with a repeatable snapshot resnaps once (`F4`)
- a rescued attempt's failure shows only as a `🫧 [withheld]` log line, never as a jest status — a
  run that rescues often looks clean in jest's summary

**edgecases + pit of success**
- a non-repeatable peer test whose name equals a stripped repeatable name would share a key, and
  the per-attempt counter reset would make both compare against one baseline. bytes that differ
  fail as an ordinary mismatch; bytes that agree pass. rare; criteria decide whether to detect it.
- two snapshots in one `then` → counters `1`, `2` per attempt, reset each attempt — stable.
- `-u` under `EVERY` → each attempt rewrites the one key; last write wins. under `SOME` → attempt 1
  writes, later attempts skip.
- `test.concurrent` inside a repeatable block: jest reads `currentConcurrentTestName` first
  (`jest-snapshot/build/index.js:1544`), so the key override would not apply. `then` never registers
  a concurrent test (`givenWhenThen.ts:393,436`); a consumer's own `test.concurrent` there is out of
  scope.
- jest version without the expected `SnapshotState` fields → throw a `MalfunctionError` that names
  the jest version, never a silent fallback.

## .open questions & assumptions

1. **[answered]** **strip vs pin (`F5`) — strip.** the wisher ruled 2026-10-05: strip the ordinal.
   any key change orphans the old keys, and an orphan (`unchecked`) fails the run outside `-u`
   (`@jest/core/build/index.js:1091,1162`), so every consumer with a repeatable snapshot resnaps once,
   guided by the migration note and the rename hint.
2. **[answered]** **semver** — `fix` (`F4`). the wisher ruled 2026-10-05: *"yes its a fix"*. the
   migration note names the one-pass resnap.
3. **[answered]** **a comment on #71** — none. the wisher ruled 2026-10-05: post no comment; once
   the change merges, close #71 as is.
4. **[research]** **vitest's key mechanism** — partly answered now: vitest builds the snapshot name
   from the task chain, `getNames(test).slice(1).join(" > ")` (`vitest/dist/chunks/vi.2VT5v0um.js:187-191`),
   not from expect state — so jest's `setState({ currentTestName })` hook has no vitest twin. the
   `given`/`when` `.repeatably` describe names carry the ordinal, so the vitest key does too. open:
   which lever strips it — a run-time rename of the suite task, an explicit snapshot hint, or names
   with no ordinal — and how vitest's per-name counter behaves across peer attempts. owed to the
   blueprint, with a vitest probe like the jest one.
5. **[answered]** **jest 29 parity** — `SnapshotState._counters` and `.unmatched` exist in jest
   `v29.7.0` (`packages/jest-snapshot/src/State.ts`) and in the installed 30.2.0;
   `suppressedErrors` exists in `v29.7.0` (`packages/expect/src/jestMatchersObject.ts`,
   `suppressedErrors: []`) and 30.2.0. both read via `gh api` / `node_modules`.
6. **[answered]** **`then.repeatably` under vitest `SOME`** — it uses native `retry`, its name
   carries no ordinal (`givenWhenThen.ts:503-510`), and vitest calls
   `snapshotClient.clearTest(file, test.id)` in `onBeforeTryTask`
   (`vitest/dist/chunks/test.B8ej_ZHS.js:196`), so each try starts fresh. no change owed there.
7. **[answered]** **what the final attempt surfaces** — by logic: the thrown-error rethrow
   (`givenWhenThen.ts:457-459`, first error of any attempt) is extant behavior outside this wish, so
   it stays; jest attaches the final attempt's own suppressed snapshot diff beside it; the
   `🫧 [withheld]` lines show the earlier failures. no wisher input needed — it changes no extant
   contract.
8. **[research]** **how the wrapper reads the test's budget** — jest keeps a per-test timeout on the
   test entry and the `jest.setTimeout` value on a global symbol; the configured `testTimeout` sits in
   circus state. which read is stable across jest 29 and 30, and what vitest offers (`testTimeout` in
   its runner config, a per-test `timeout`), is owed to the blueprint, with a probe per runner. the
   fallback, if no read is stable: the wrapper takes an explicit `timeout` in the `repeatably`
   configuration.
9. **[answered]** **scope: timeouts and hook failures ride in this change (`F6`).** the wisher ruled
   2026-10-05: *"this is the point to solve"*. a non-final `SOME` attempt absorbs a timeout, a setup
   failure, and a snapshot mismatch alike; B7 and B8 are bars of this change.

## .what is awkward

- **the fix reaches into a test runner's private state.** that is the price of a retry inside one
  jest test file without `jest.retryTimes`. contained, clamped by tests, fail-fast — but it is a
  dependency on internals.
- **the issue's diagnosis is wrong and its bars are mostly right.** B1, B4, B5 already pass for a
  thrown failure; they become clamps, not fixes. the real fix is what #71 did not name: *any failure
  in a non-final `SOME` attempt must be retried* — the snapshot variant of B4, plus B7 and B8.
- **a forced resnap for a `fix`.** honest, but it lands on every consumer at once.
- **a timed-out drive keeps a ghost.** js cannot cancel a promise, so attempt 1's slow call runs on
  beside attempt 2. its result is discarded, but its side effects (a temp dir, a spend) still land.
- **a raw jest hook stays outside the retry.** only `useBeforeAll` / `useBeforeEach` are ours to
  absorb; a plain `beforeAll` that throws still reds the file. the readme must say so plainly.
