# vision: progress reporter

## the outcome world

### before

```bash
# run integration tests
npm run test:integration

# ... wait 5 minutes staring at dots ...
# ... no idea how far along we are ...
# ... finally see "42 passed, 3 failed" at the end
```

the human runs tests. sits. waits. wonders. "is it stuck? how many passed? should i grab coffee?"

when tests fail, they scroll through terminal output hunting for the failure. or worse — the output scrolled past and they have to re-run.

### after

```bash
# terminal 1: run tests with progress tracking
npm run test:integration -- --progress .log/test/progress/integration

# terminal 2: watch progress in real-time
watch -n1 'tail -1 .log/test/progress/integration/progress.overview.jsonl | jq'
# {"passed":127,"failed":2,"remains":43,"outof":172,"duration":"PT2M34S"}

# terminal 3: react to failures as they happen
tail -f .log/test/progress/integration/progress.failures.jsonl | jq -r '.suite'
# src/domain/auth/login.integration.test.ts
# src/domain/billing/invoice.integration.test.ts
```

### the "aha" moment

a shell skill watches `progress.failures.jsonl`. the moment a test fails, it:
- opens the file in the editor
- shows the failure context
- lets the mechanic fix while tests continue running

no more waiting for the full suite. failures surface immediately. fixes happen in parallel.

## user experience

### usecase 1: human monitors long test run

```bash
# start tests
npm run test:integration -- --progress .log/test/progress/integration &

# check progress anytime
cat .log/test/progress/integration/progress.overview.jsonl | tail -1 | jq
```

### usecase 2: mechanic skill reacts to failures

```bash
# skill watches for failures
tail -f .log/test/progress/integration/progress.failures.jsonl | while read line; do
  path=$(echo "$line" | jq -r '.path')
  suite=$(echo "$line" | jq -r '.suite')
  echo "🔴 failure detected: $suite in $path"
  # trigger fix workflow...
done
```

### usecase 3: ci pipeline surfaces progress

```bash
# ci skill polls and reports
while true; do
  status=$(tail -1 .log/test/progress/integration/progress.overview.jsonl)
  passed=$(echo "$status" | jq '.passed')
  outof=$(echo "$status" | jq '.outof')
  echo "::notice::tests: $passed/$outof"
  sleep 10
done &

npm run test:integration -- --progress .log/test/progress/integration
```

### contract: inputs

| input | type | description |
|-------|------|-------------|
| `--progress` | path | directory to write progress files |

### contract: outputs

**progress.overview.jsonl** — one line per heartbeat (~1s)
```jsonl
{"passed":0,"failed":0,"remains":172,"outof":172,"duration":"PT0S"}
{"passed":12,"failed":0,"remains":160,"outof":172,"duration":"PT8S"}
{"passed":45,"failed":1,"remains":126,"outof":172,"duration":"PT31S"}
```

**progress.failures.jsonl** — one line per failure
```jsonl
{"path":"src/domain/auth/login.integration.test.ts","suite":"login flow › [case1] valid credentials › [t0] submits","failure":"Error: expected 200 got 401","stdout":"...","stderr":"..."}
```

note:
- `failure` = from runner (assertion errors + stack traces)
- `stdout` = from run (console.log)
- `stderr` = from run (console.warn/error)

### timeline

1. human invokes `npm run test:integration -- --progress .log/test/progress/integration`
2. reporter creates directory if absent
3. reporter writes initial overview line (all remains)
4. tests run; overview updates every ~1 second
5. on failure: append to failures.jsonl immediately
6. test run completes; final overview line written
7. consumer tools read files, react, report

## mental model

### how users describe it

> "it's like a progress bar for tests, but machine-readable"

> "test results stream to files so other tools can watch"

> "failures show up in a file the moment they happen, not at the end"

### analogies

- **build log streaming**: like how ci systems stream build output in real-time
- **tail -f for tests**: watch test progress like watching a log file
- **event sourcing**: every state change (pass/fail) is an event in a log

### terms

| user says | we call it |
|-----------|------------|
| "progress file" | progress.overview.jsonl |
| "failure log" | progress.failures.jsonl |
| "heartbeat" | overview line (emitted ~1s) |
| "test count" | outof |
| "remaining" | remains |

## evaluation

### how well does it solve the goals?

| goal | solved? | notes |
|------|---------|-------|
| know progress mid-run | ✅ | overview.jsonl heartbeat |
| react to failures immediately | ✅ | failures.jsonl streams |
| programmatic access | ✅ | jsonl = one jq away |
| human readable | ✅ | jsonl + jq = pretty |
| minimal overhead | ✅ | append-only writes |

### pros

- **simple**: two files, append-only, jsonl
- **composable**: any tool can tail/parse
- **immediate**: failures surface instantly
- **resumable**: jsonl survives crashes

### cons

- **extra flag**: user must remember `--progress`
- **disk writes**: adds i/o (minimal, append-only)
- **directory management**: user picks path

### pit of success

| edgecase | handling |
|----------|----------|
| directory doesn't exist | reporter creates it |
| file already exists | append (don't overwrite) — enables resume |
| test crashes mid-run | last heartbeat shows state before crash |
| no failures | failures.jsonl exists but empty |

## open questions & assumptions

### assumptions

1. **jsonl format**: one json object per line — simple, streamable, greppable
2. **heartbeat ~1s**: frequent enough to feel real-time, rare enough to minimize i/o
3. **iso duration**: `PT2M34S` format for duration (iso 8601)
4. **stdout/stderr capture**: failures include full output

### questions for wisher

1. [answered: explicit path] require explicit path always, no magic `auto` value
2. [answered: yes, 10kb max] truncate stdout/stderr in failures.jsonl if huge
3. [answered: no, counts only] should overview include test names in progress, or just counts?
4. [answered: yes] emit `progress.summary.json` at end with final state
5. [answered: yes] should overview include `skipped` count? (jest has skipped/todo states beyond pass/fail)
6. [answered: PT2M34S] use iso 8601 duration format via `asIsoDuration` from iso-time package
7. [answered: reporter config] how should `--progress` be passed? use reporter config in jest.config.js, same pattern as extant slowtest reporter:
   ```ts
   reporters: [['test-fns/progress.reporter.jest', { dir: '.log/test/progress' }]]
   ```

## what is awkward?

### forced tradeoffs

- **path vs auto**: requiring explicit path is explicit but verbose
- **two files vs one**: separate overview/failures is clean but means two watches

### mental model friction

- **jsonl vs json**: some users expect `.json` and try to parse whole file
- **heartbeat timing**: "once per second" is approximate — depends on test timing

### uncomfortable bits

- **stdout/stderr size**: failures with huge output could bloat failures.jsonl
- **no test name in overview**: overview shows counts, not which test is running — simpler but less informative
