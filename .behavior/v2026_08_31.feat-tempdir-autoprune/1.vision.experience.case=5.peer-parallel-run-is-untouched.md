# case=5 — the peer-parallel run is untouched

> cell 5 · `hooks=jest|vitest` · `termination=pass` · `peer-parallel` · `reclaim`
> **feel** ⚡ **sharp** · **care** critipath — **the densest cell in the grid**

## why this is the cell that matters most

every other cell in this behavior fails toward **leak**. this one is the only cell that can fail
toward **loss**.

a wrong reap here does not waste disk. it deletes a directory that another live process is
actively reading and writing — mid-test, mid-`git commit`, mid-fixture-clone. the victim run does
not fail cleanly; it fails with `ENOENT` in a place that makes no sense, and its human spends an
afternoon on a defect that was never theirs.

**cost is near-maximal. frequency is not low.** verified live on this machine today,
`/tmp/test-fns/` holds three `rhachet.*` worktree scopes side by side — and #66 will merge those
three into one shared scope, which raises the frequency further. two runs that share a contained
dir is the normal case, not the exotic one.

## the narrative

kai runs the full suite in one terminal. it takes four minutes.

two minutes in, kai switches to a second worktree and runs a scoped suite there. it finishes in
twelve seconds and its teardown fires — while kai's first run is still mid-flight, with 200 live
fixture dirs in the same contained directory.

no event kai would notice occurs. the first run finishes green.

that non-event is the entire deliverable of this cell.

## how it fails safe — by construction, not by check

peer-safety is a property of the **name**, never of a runtime test.

```
2026-08-31T14-22-01.443Z.r7f3a91c2.my-test.a1b2c3d4
                        └─────────┘
                        the run id — the reclaim's ONLY filter
```

the reclaim reads the contained dir and removes the entries whose name carries **its own** run id.
a peer's dirs carry a different id, so they are not candidates. there is no liveness probe to get
wrong, no timestamp race to lose, no lock to leak.

this is the wish's first-named hazard, and the prior-art hazard from `work.harness.ts`:

> **never prune by a bare prefix glob.** the filter must be the run, never the class prefix —
> otherwise a parallel run takes a peer's live dirs.

### the three shapes this rejects

| tempting shape | how it kills a peer |
|---|---|
| reap every dir in the contained dir | reaps 100% of the peer's live fixtures |
| reap every dir older than the run's start | the peer started earlier — reaps all of its |
| reap every dir whose owner pid is dead | pid reuse and container boundaries make the claim unsound |

each is a one-line change away from correct, and each is catastrophic. that is what makes this
cell **sharp** rather than merely important.

## the timeline

```gherkin
given('[case5] two enhooked runs that share one contained dir, concurrently', () => {
  // the contained dir is NOT assumed empty — it may already hold a prior run's
  // residue, another repo's dirs, or the two infra files genIsolatedTempInfra
  // writes. every count below is either run-scoped or measured against this.
  //
  // ⚠️ RA and RB are bound here, never read as free variables below. a repair
  //    that binds one term alone leaves the class intact — the whole cast owes
  //    a declaration up front.
  const { pathPhysical } = getOneTempDirRoot();
  const countBefore = countTempDirs(pathPhysical);
  const RA = useThen('run A starts in one worktree', () => mintRun());
  const RB = useThen('run B starts in a peer worktree, while A is live', () => mintRun());

  when('[t0] run A starts and allocates 200 dirs under run id RA', () => {
    then('all 200 carry RA', () => {
      expect(countTempDirs(pathPhysical, { run: RA })).toEqual(200);
    });
  });

  when('[t1] run B starts, allocates 5 dirs under RB, while A is still live', () => {
    then('the contained dir holds both sets', () => {
      expect(countTempDirs(pathPhysical, { run: RA })).toEqual(200);
      expect(countTempDirs(pathPhysical, { run: RB })).toEqual(5);
    });
  });

  when('[t2] run B finishes FIRST and its global teardown fires', () => {
    then('run B reclaimed exactly its own 5', () => {
      expect(countTempDirs(pathPhysical, { run: RB })).toEqual(0);
    });

    then('run A\'s 200 live dirs are ALL untouched', () => {
      expect(countTempDirs(pathPhysical, { run: RA })).toEqual(200);
    });

    then('every one of run A\'s dirs is still readable', () => {
      // ⚠️ `dirsOf(R)` is the form — the same one [t4] uses — never a local
      //    alias like `dirsOfRunA` that no cast declares. this file's cast
      //    comment claims every handle is declared up front, and this handle
      //    is. it carries the readable-contents half of the peer-safety proof:
      //    an unbound term throws rather than evaluates, and then the assertion
      //    is not there at all.
      for (const dir of dirsOf(RA)) expect(existsSync(dir)).toEqual(true);
    });
  });

  when('[t3] run A then finishes and its teardown fires', () => {
    // ⚠️ the teardown's own report of what it CONSIDERED, minted in-body —
    //    never a bare `reclaimAudit` bound nowhere. this is the assertion
    //    this whole cell turns on: it is what separates a reclaim whose
    //    candidate set is narrow AT THE SOURCE from one that considers every
    //    dir and then filters. unbound, it throws rather than evaluates, so a
    //    considers-then-reaps implementation reads identical to a correct one.
    const auditOfRA = useThen('the teardown yields the set it considered', () =>
      runTeardownFor(RA),
    );

    then('run A reclaims its own 200', () => {
      expect(countTempDirs(pathPhysical, { run: RA })).toEqual(0);
    });

    then('run A never saw run B\'s dirs as candidates', () => {
      expect(auditOfRA.candidatesConsidered).not.toContain(RB);
    });

    // both runs have now finished, so BOTH populations are empty and the whole
    // dir does return to countBefore. each term names its population anyway —
    // the equality is then a CONSEQUENCE of the two run-scoped facts above it,
    // rather than a bare claim over a shared namespace.
    then('both populations are empty, so the shared dir returns to its prior count', () => {
      expect(countTempDirs(pathPhysical, { run: RA })).toEqual(0);
      expect(countTempDirs(pathPhysical, { run: RB })).toEqual(0);  // reclaimed at [t2]
      expect(countTempDirs(pathPhysical)).toEqual(countBefore);
    });
  });

  // 🔴 cells 6, 8, 8c — peer-parallel crossed with the OTHER three terminations.
  // [t0]–[t3] run a peer beside a
  // run that PASSES; cells 6/8/8c are the same peer beside a run that fails,
  // is interrupted, or is force-exited. the catalog subsumed all three into
  // this file on a REASONING step — "peer-safety is a property of the name,
  // fixed at allocation, so termination cannot reach it" — which is sound and
  // is not a timeline. the identical shape as cell 3c, one region over.
  when('[t4] the peer stays live while OUR run ends three other ways', () => {
    const RLive = useThen('a peer run starts and stays live throughout', () => mintRun());
    const dirsMadeByPeer = useThen('the peer allocates its fixtures', () =>
      countTempDirs(pathPhysical, { run: RLive }),
    );
    const RFail  = useThen('our run FAILS a test, then its teardown fires', () =>
      mintRun({ willFail: true }),
    );
    const RKill  = useThen('our run is SIGKILLed mid-flight', () => mintRun({ kill: true }));
    // ⚠️ RForce is SCOPED as well as force-exited, because
    //    `scoped × preempted × peer-parallel` is verdicted nowhere else.
    //    it folds into cell 8c, because peer-safety is a property of the NAME
    //    and reads neither coverage nor termination. this mint makes the demo
    //    EXERCISE that fold rather than merely assert it — and it is this
    //    repo's default invocation (`--changedSince=main --forceExit`) run
    //    beside a second worktree, so it is the likeliest shape on this machine.
    const RForce = useThen('our run is SCOPED and killed by a signal mid-run', () =>
      mintScopedRun({ preempted: true }),
    );

    then('cell 6 — a FAILED run reclaims its own and spares the peer', () => {
      expect(countTempDirs(pathPhysical, { run: RFail })).toEqual(0);
      expect(countTempDirs(pathPhysical, { run: RLive })).toEqual(dirsMadeByPeer);
    });

    then('cell 8 — an INTERRUPTED run reclaims none, so the peer is trivially safe', () => {
      expect(countTempDirs(pathPhysical, { run: RKill })).toBeGreaterThan(0);  // leaks
      expect(countTempDirs(pathPhysical, { run: RLive })).toEqual(dirsMadeByPeer);
    });

    then('cell 8c — a SCOPED, FORCE-EXITED run leaks its own and spares the peer', () => {
      // 8c holds BOTH coverages: the scope narrows what THIS run would have
      // reclaimed, and reaches the peer not at all. that is the fold stated in
      // the inventory's region 1 note, exercised here rather than asserted.
      expect(countTempDirs(pathPhysical, { run: RForce })).toBeGreaterThan(0);
      expect(countTempDirs(pathPhysical, { run: RLive })).toEqual(dirsMadeByPeer);
    });

    then('and in all three the peer\'s dirs are still READABLE, never half-removed', () => {
      // loss, not leak, is the failure this cell exists to forbid
      for (const dir of dirsOf(RLive)) expect(existsSync(dir)).toEqual(true);
    });
  });

  // 🔴 cell 24 — two runner invocations in ONE command, concurrently.
  // `npm-run-all --parallel` is the shape; the catalog subsumed it here on the
  // same reasoning-not-timeline argument. it differs from [t0]-[t3] in ONE
  // respect that matters: the two runs share a parent process and a cwd, so an
  // implementation that keyed on either would fuse them.
  when('[t5] both runs are invocations of ONE command, in one cwd', () => {
    const [R1, R2] = useThen('two runners start in parallel from one command', () =>
      mintParallelRuns({ command: 'npm-run-all --parallel test:unit test:integration' }),
    );

    then('they mint DIFFERENT ids, despite one parent and one cwd', () => {
      // the assertion cell 24 exists for: a mint keyed on pid-of-parent or on
      // cwd would hand both runs the same id, and each would reap the other.
      expect(R1).not.toEqual(R2);
    });

    then('each reclaims exactly its own', () => {
      expect(countTempDirs(pathPhysical, { run: R1 })).toEqual(0);
      expect(countTempDirs(pathPhysical, { run: R2 })).toEqual(0);
    });
  });
});
```

> 🟠 **`[t3]`'s last assertion is the unfiltered `countTempDirs(pathPhysical) === countBefore`, and
> it is TRUE here.** one plausible "repair" turns it into `=== countBefore + 150`, on the premise
> that *run B is still live*. **run B is not still live** — `[t2]` says B finishes **first** and
> reclaims its own 5. the live-peer premise (and the literal `150`) belongs to `case=12`'s timeline,
> where a peer genuinely is live; carried here it contradicts the two steps above it, because B
> cannot be reclaimed at `[t2]` and hold 150 dirs at `[t3]`. `countBefore` must also be established
> inside this timeline, or the assertion rests on a free variable.
>
> **two lessons, and the second is the one that costs more:**
>
> 1. an unfiltered count over a shared namespace is unsound **as a standalone claim**. it is fine as
>    a **consequence** of run-scoped facts asserted beside it — which is how `[t3]` reads.
> 2. **a general rule does not tell you which local premise holds.** "shared namespace ⇒ the peer's
>    dirs are still there", applied without a re-read of the two steps above it, converts a correct
>    assertion into a confident wrong one. a sweep driven by a rule must still re-derive each site's
>    own preconditions.

## the two assertions a reviewer must demand

- **`[t2]` third `then`** — `existsSync` on each of A's dirs, not merely a count. a count can pass
  while the *contents* were emptied; this cell is about a live process's data.
- **`[t3]` second `then`** — that A never *considered* B's dirs. an implementation that considers
  then filters is one refactor away from an implementation that considers then reaps. the
  candidate set must be narrow at the source.

## the seam to #66, named

today the worktree keying gives **accidental** peer-safety across worktrees. #66 removes it. this
cell must hold under **both** the current per-worktree scope and #66's shared-per-repo scope,
because the guarantee here is a property of the name, not of the directory layout.

that independence is precisely why the wish can send #64 and #66 in either order.
